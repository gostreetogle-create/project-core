## ФАЗА 1: БЕЗОПАСНОСТЬ СЕРВЕРА

> **Почему это первое:** Сервер — фундамент. Если он дырявый, всё остальное не имеет смысла. Другой AI посмотрит на сервер без защиты и сразу скажет «халтура».

---

### Пункт 1.1 — Поставить «щит» от веб-атак (helmet)

**Что делаем:** Устанавливаем готовый пакет `helmet`, который автоматически закрывает 10+ типовых уязвимостей веб-сервера.

**Человеческим языком:** Это как повесить на окна решётки и поставить сигнализацию. Хакер не увидит, на чём написан сайт, не сможет вставить свой код через уязвимости в заголовках.

**Где:** `backend/src/index.ts`
**Как проверить:** Открыть сайт в браузере → F12 → вкладка Network → найти любой ответ сервера → в заголовках НЕ должно быть `X-Powered-By: Express`. Должны быть `X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy` и другие защитные заголовки.

**Сложность:** Низкая (добавить 1 строку + установка пакета)

---

### Пункт 1.2 — Ограничить размер запросов (express.json limit)

**Что делаем:** Указываем серверу: «не принимай запросы больше 1 мегабайта».

**Человеческим языком:** Злоумышленник может отправить запрос размером 1 гигабайт — сервер попытается его обработать и упадёт. Сайт перестанет работать для всех. Мы ставим шлагбаум: всё что больше лимита — отбрасывается сразу, даже не читая.

**Где:** `backend/src/index.ts`, строка `app.use(express.json())`
**Как проверить:** Отправить запрос с телом больше 1 МБ → сервер должен вернуть ошибку 413 (Payload Too Large).

**Сложность:** Низкая (изменить 1 строку)

---

### Пункт 1.3 — Защита от перебора паролей (rate-limit)

**Что делаем:** Устанавливаем ограничение: не больше 5 попыток входа с одного адреса за 15 минут.

**Человеческим языком:** Хакер запускает программу, которая перебирает 1000 паролей в секунду. Без защиты — за минуту подберёт. С защитой — после 5 неудачных попыток сервер 15 минут игнорирует запросы с этого адреса. Взлом становится невозможным.

**Где:** `backend/src/index.ts`, добавить middleware на маршрут `/api/v1/auth/login`
**Как проверить:** 6 раз подряд ввести неверный пароль → на 6-й раз получить ошибку «слишком много попыток».

**Сложность:** Низкая (установка пакета + 3 строки кода)

---

### Пункт 1.4 — Безопасное хранение «долгосрочного ключа» (refresh-токен через cookie)

**Что делаем:** Меняем способ хранения refresh-токена: вместо «записной книжки на столе» (localStorage, доступной любому скрипту) — «запечатанный конверт» (HttpOnly cookie, недоступный для JavaScript).

**Человеческим языком:** Сейчас refresh-токен хранится в localStorage — это как оставить ключ от квартиры под ковриком. Любой вирус в браузере может его прочитать. HttpOnly cookie — это как отдать ключ на хранение банку: только банк (сервер) может его прочитать, вирус не доберётся.

**Где:**
- **Бэкенд:** `backend/src/modules/auth.routes.ts` — добавить установку cookie с флагами `httpOnly`, `secure`, `sameSite`
- **Фронтенд:** `src/app/core/auth.service.ts` — убрать refreshToken из localStorage, читать из cookie только на бэкенде

**Как проверить:** После входа в систему — открыть DevTools (F12) → Application → Cookies → должен быть `refreshToken` с флагами HttpOnly и Secure. В localStorage должен быть ТОЛЬКО accessToken.

**Сложность:** Средняя (затрагивает и бэкенд, и фронтенд)

---

### Пункт 1.5 — Починить сборку для сервера (Dockerfile)

**Что делаем:** Меняем способ запуска бэкенда в Docker: вместо компиляции TypeScript (которая ломает импорты) — запускаем через `tsx` (инструмент, который умеет запускать TypeScript напрямую).

**Человеческим языком:** Сейчас Docker-образ собран неправильно — при запуске на сервере падает с ошибкой. Это как построить дом, но забыть подключить электричество. Исправляем.

**Где:** `backend/Dockerfile`
**Как проверить:** `docker compose up --build` → backend должен запуститься без ошибок.

**Сложность:** Средняя

### Пункт 2.1 — Добавить «энергосберегающий режим» в страницу входа и оболочку (OnPush)

**Где:** `src/app/features/login/login.component.ts`, `src/app/layout/admin-layout.component.ts`
**Как проверить:** Открыть код → в декораторе `@Component` должна быть строчка `changeDetection: ChangeDetectionStrategy.OnPush`

**Сложность:** Низкая (добавить 1 строку в 2 файла)

**Где:** `src/app/core/auth.service.ts`
**Как проверить:** В методе `login()` тип возврата должен быть `Observable<ApiResponse<LoginResponse>>` (используя типы из `shared/types/`)

## ФАЗА 3: АВТОМАТИЧЕСКОЕ ПРОДЛЕНИЕ СЕССИИ

> **Почему это третье:** Сейчас пользователь через 24 часа вылетает из системы. Надо чтобы сессия продлевалась сама, без участия человека.

---

### Пункт 3.1 — Автоматическое обновление токена при ошибке 401

**Что делаем:** В перехватчике запросов (`auth.interceptor.ts`) добавляем логику: если сервер ответил «токен истёк» (ошибка 401) — автоматически запрашиваем новый токен и повторяем исходный запрос.

**Человеческим языком:** Это как водительские права: когда срок истекает, вы их продлеваете и продолжаете ездить. А не начинаете жизнь с нуля. Сейчас система при истечении токена просто «выбрасывает» пользователя — надо заново входить. Будет: токен истёк → система сама продлила → работает дальше. Пользователь даже не заметил.

**Где:** `src/app/core/auth.interceptor.ts`
**Как проверить:** Войти в систему → подождать (или вручную сделать токен истёкшим) → сделать любое действие → система должна молча обновить токен и продолжить работу.

**Сложность:** Средняя (логика с очередью запросов и флагом «уже обновляется»)

---

### Пункт 3.2 — Проверять срок годности токена при загрузке

**Что делаем:** При старте приложения проверяем, не истёк ли сохранённый токен. Если истёк — не показываем пользователя как «залогиненного», а сразу разлогиниваем.

**Человеческим языком:** Сейчас система смотрит на токен и говорит «есть токен — значит пользователь в системе». Но токен мог истечь 3 дня назад. Это как показывать просроченный пропуск. Исправляем: проверяем дату окончания.

**Где:** `src/app/core/auth.service.ts` → метод `loadUserFromStorage()`
**Как проверить:** Взять истёкший токен, записать в localStorage → обновить страницу → система НЕ должна считать пользователя залогиненным.

**Сложность:** Низкая (добавить 3 строки проверки)

## ФАЗА 4: НАДЁЖНОСТЬ СЕРВЕРА

> **Почему это четвёртое:** Сервер должен уметь «красиво» выключаться и вести логи (журнал событий).

---

### Пункт 4.1 — «Красивое» выключение сервера (Graceful Shutdown)

**Что делаем:** Добавляем обработку сигнала «выключение»: перед тем как выключиться — закрываем соединение с базой данных и завершаем текущие запросы.

**Человеческим языком:** Сейчас если сервер выключают (команда `docker stop`) — он обрывается мгновенно. Как если бы вы выдёргивали вилку из розетки вместо нормального выключения. Можно потерять данные. Исправляем: сервер научится «прощаться» — завершит дела и только потом выключится.

**Где:** `backend/src/index.ts`
**Как проверить:** Запустить сервер, отправить `docker stop` → в логах должно быть «Shutting down gracefully...», а не мгновенное обрыв.

**Сложность:** Низкая (10 строк кода)

---

### Пункт 4.2 — Настроить нормальные логи (pino)

**Что делаем:** Заменяем `console.log` на структурированные логи через библиотеку `pino`.

**Человеческим языком:** Сейчас сервер «пишет в блокнот от руки» — `console.log('что-то случилось')`. Это неудобно: нельзя отфильтровать только ошибки, нельзя понять когда что произошло, нельзя искать. Ставим нормальную систему: каждая запись имеет уровень (ошибка/предупреждение/инфо), время, контекст. Можно искать, фильтровать, анализировать.

**Где:** Весь backend (создать `config/logger.ts`, заменить все `console.*`)
**Как проверить:** Запустить сервер → вместо `[SERVER] Running on...` должен быть структурированный JSON-лог с timestamp и level.

**Сложность:** Средняя (замена во всех файлах бэкенда)

## ФАЗА 8: УЛУЧШЕНИЯ ДЛЯ РАЗРАБОТЧИКОВ

> **Почему это восьмое:** Это то, что делает проект «взрослым» — автоматическая проверка при каждом изменении кода, обработка ошибок.

### Пункт 8.1 — CI/CD (автоматическая проверка при пуше)

**Что делаем:** Создаём GitHub Actions workflow: при каждом пуше автоматически запускается проверка кода → сборка → тесты.

**Человеческим языком:** Это как автоматический контролёр качества: как только кто-то вносит изменения — робот сразу проверяет «всё ли работает». Если что-то сломалось — робот скажет «стоп, ошибка».

**Где:** `.github/workflows/ci.yml` (новый файл)
**Как проверить:** Пуш в репозиторий → на вкладке Actions появляется зелёная галочка.

**Сложность:** Средняя

### Пункт 8.2 — Обработчик ошибок на фронтенде (GlobalErrorHandler)

**Что делаем:** Создаём сервис, который ловит ВСЕ непойманные ошибки в приложении и показывает пользователю понятное сообщение вместо «красного экрана».

**Человеческим языком:** Сейчас если в коде ошибка — пользователь видит страшную красную простыню в консоли. Будет: пользователь видит «Что-то пошло не так, попробуйте позже», а разработчик (или AI) получает детали ошибки.

**Где:** `src/app/core/global-error-handler.ts` + регистрация в `app.config.ts`
**Как проверить:** Сделать ошибку в коде → пользователь видит красивое сообщение, а не пустой экран.

**Сложность:** Низкая
